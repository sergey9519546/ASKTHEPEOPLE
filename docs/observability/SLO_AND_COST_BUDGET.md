# Service level objectives and cost budgets

This document is the operational reference for the two Gate 4 resource controls
that can be declared **without a new dependency**: the service level objectives
for the HTTP API, and the per-run and per-day cost ceilings.

> **Gate status is not recorded here.**
> [`architecture/index.md` § *Status of record*](../architecture/index.md#status-of-record)
> is the single authoritative statement of gate status. This document records
> what one slice of that gate does and does not do. Where the two appear to
> disagree, `index.md` wins and this file is the bug.

The declared state vocabulary is the one defined in
[`architecture/index.md` § *State legend*](../architecture/index.md#state-legend-used-in-this-document):
**CURRENT**, **PARTIAL**, **TARGET**, **TRANSITION**.

## What this covers and what it does not

| Concern | State | Where it lives |
|---|---|---|
| Request count, latency histogram, in-flight depth | CURRENT | [`backend/app/utils/metrics.py`](../../backend/app/utils/metrics.py), served at `GET /health/metrics` by [`backend/app/api/health.py`](../../backend/app/api/health.py) |
| SLO objectives declared as operator-settable configuration | CURRENT | [`backend/app/config.py`](../../backend/app/config.py) |
| Alerting rules that fire on those objectives | TARGET | not built |
| A measurement of what a run costs | TARGET | not built |
| Enforcement of a cost ceiling at run admission | TARGET | not built |
| Distributed tracing | TARGET | not built; see *Remaining gaps* |

No module reads the settings documented here. That is deliberate and is stated
plainly rather than implied: declaring an objective and enforcing one are
different changes, and the enforcement half depends on a cost meter that does
not exist.

## SLO definitions

The objectives are declared over the series the metrics endpoint already
exposes. They do not name an invented metric, and they cannot: the exposition
is generated by `render_prometheus` in
[`backend/app/utils/metrics.py:157`](../../backend/app/utils/metrics.py) and the
bucket boundaries are the module-level `LATENCY_BUCKETS` tuple at
[`:47`](../../backend/app/utils/metrics.py), fixed at
`0.005 0.01 0.025 0.05 0.1 0.25 0.5 1.0 2.5 5.0 10.0` seconds.

### The two objectives

**Availability (error rate).** The share of `5xx` responses must stay at or
below `SLO_ERROR_RATE_MAX_RATIO` over `SLO_WINDOW_SECONDS`.

```text
good_events = sum(rate(askthepeople_http_requests_total[window]))
             - sum(rate(askthepeople_http_requests_total{status_class="5xx"}[window]))
objective   = good_events / sum(rate(askthepeople_http_requests_total[window]))
             >= 1 - SLO_ERROR_RATE_MAX_RATIO
```

**Latency.** The share of requests finishing at or under
`SLO_LATENCY_BUCKET_SECONDS` must stay at or above `SLO_LATENCY_TARGET_RATIO`
over `SLO_WINDOW_SECONDS`.

```text
good_events = sum(rate(askthepeople_http_request_duration_bucket{le="<SLO_LATENCY_BUCKET_SECONDS>"}[window]))
objective   = good_events / sum(rate(askthepeople_http_request_duration_bucket{le="+Inf"}[window]))
             >= SLO_LATENCY_TARGET_RATIO
```

Two properties of these definitions are worth stating because they are the
difference between an SLO and a decoration:

- **Both objectives are computed from the same request counter.** An objective
  cannot be satisfied by serving less traffic, and one cannot be met by failing
  faster.
- **`SLO_LATENCY_BUCKET_SECONDS` must be one of `LATENCY_BUCKETS`.** The
  histogram can only answer "what share finished under X" for X it has a bucket
  at. A threshold between buckets names a percentile the endpoint cannot
  report, so `Config.validate_production_gates` refuses it at startup rather
  than letting an operator adopt an unmeasurable objective. See
  [`backend/app/config.py:502`](../../backend/app/config.py).

### Settings

| Setting | Env var | Default | Why this default |
|---|---|---|---|
| `SLO_ENABLED` | `SLO_ENABLED` | `False` | An SLO is a commitment an operator adopts, not a property the code confers. Off means none of the values below asserts anything. |
| `SLO_LATENCY_BUCKET_SECONDS` | `SLO_LATENCY_BUCKET_SECONDS` | `1.0` | The boundary between "a person is still waiting" and "they navigated away", and a real bucket in `LATENCY_BUCKETS`. |
| `SLO_LATENCY_TARGET_RATIO` | `SLO_LATENCY_TARGET_RATIO` | `0.99` | One request in a hundred may be slow because a provider was cold. That is normal operation, not an incident. |
| `SLO_ERROR_RATE_MAX_RATIO` | `SLO_ERROR_RATE_MAX_RATIO` | `0.001` | Deliberately stricter than the latency objective: a slow answer is degraded service, a `5xx` is a broken contract. |
| `SLO_WINDOW_SECONDS` | `SLO_WINDOW_SECONDS` | `2592000` | 30 days spans a weekly cycle, so a quiet weekend cannot pass an objective a busy Monday would fail. |
| `SLO_MIN_REQUESTS` | `SLO_MIN_REQUESTS` | `20` | Below this many requests the ratios are arithmetic on a handful of points. The objective is reported as not evaluated rather than as compliant. |

### What "evaluated" means today

Nothing evaluates these values. An operator who sets them has declared a
threshold and must build the recording and alerting rules to compare against it;
the formulas above are the specification for those rules, expressed against
series that exist so the rules cannot be written against a metric that was never
exported. The one part that is enforced is the *shape* of the declaration, which
§ *Refusals* covers.

## Cost budgets

### The measurement that does not exist

A cost ceiling can only be enforced against a measured cost. The tree contains
no measurement of one. The provider response is read for its content only at
[`backend/app/utils/llm_client.py:108`](../../backend/app/utils/llm_client.py)
— `response.choices[0].message.content` — and its `usage` payload is discarded,
so prompt and completion tokens are never recorded, let alone priced. There is
no price table, no token accounting, and no per-run cost field anywhere under
`backend/app`.

This is the whole reason the breach-action decision below is constrained rather
than free. It is recorded here so no reader has to re-derive it, and so the
first change that adds a cost meter knows which configuration it is completing.

### Settings

| Setting | Env var | Default | Why this default |
|---|---|---|---|
| `COST_BUDGET_ENABLED` | `COST_BUDGET_ENABLED` | `False` | Opt-in, matching every other resource control in `Config`. Declaring a budget an operator has not chosen is not a safe default. |
| `COST_BUDGET_MAX_USD_PER_RUN` | `COST_BUDGET_MAX_USD_PER_RUN` | `0.0` | `0.0` means "no per-run ceiling declared", not "free". A run is the unit an operator can actually refuse. |
| `COST_BUDGET_MAX_USD_PER_DAY` | `COST_BUDGET_MAX_USD_PER_DAY` | `0.0` | The daily ceiling is the scope that fails independently: many cheap runs are only visible in the total the provider invoice arrives as. |
| `COST_BUDGET_BREACH_ACTION` | `COST_BUDGET_BREACH_ACTION` | `warn` | The only value that is honest today, because there is no meter that could make a stronger claim. |

The two ceilings are separate rather than one ceiling plus a period because they
fail independently, and a single knob would force an operator to pick one and
leave the other unbounded.

### Breach action: `refuse` is the target, `warn` is the only selectable value

**Decision.** `COST_BUDGET_BREACH_ACTION` accepts `warn` and `refuse`
(`COST_BUDGET_BREACH_ACTIONS` at
[`backend/app/config.py:107`](../../backend/app/config.py)). `warn` is the
default. Selecting `refuse` in production **refuses to boot** and names the
seam the refusal must be wired into.

**Why refusing is the right target.** This is a pre-release product with no
revenue per run to protect and an explicit fail-closed posture in the security
invariants. A run that will breach its ceiling should be stopped before it is
enqueued, not after the spend, because the spend is the thing being bounded and
it is not recoverable. `warn` after the fact bounds nothing.

**Why `refuse` cannot be selected yet.** Because no code path consults the
ceiling. Selecting it would make an operator read "runs that would breach their
budget are refused" and receive an unbudgeted run. A boot failure is the cheaper
of the two wrong outcomes: it is noticed immediately, and it cannot be mistaken
for a working control. The refusal message names `run_preflight` in
[`backend/app/services/simulation_preflight.py:421`](../../backend/app/services/simulation_preflight.py)
as the place the check belongs, because that is the existing pre-run admission
gate that already calls `Config.validate()`.

**Why `degrade` is not supported at all.** There is no reduced-fidelity run
mode in the tree: no cheaper model tier, no partial-output contract, and no
declared quality floor. Substituting one silently would change what the output
claims to be, which reaches into the truth boundary in
[`architecture/adr/ADR-0001-product-category-and-truth-contract.md`](../architecture/adr/ADR-0001-product-category-and-truth-contract.md).
`degrade` is not in the accepted set rather than being accepted and ignored.

**The tradeoff, stated.** The cost of this decision is that the useful action
cannot be turned on yet. An operator who wants their ceiling enforced today must
either wait for the meter or hold the limit outside the application, for example
with a provider-side spending cap. The cost of the alternative — accepting
`refuse` and documenting it as aspirational — is a control that reads as active
and is not, which is the failure mode this repository's release-gate discipline
exists to prevent. A boot failure is preferable to a green dashboard over an
unenforced budget.

## Refusals

Both refusal paths are in the **gateway**, not only in `validate()`. This is
deliberate and follows a measured failure: `Config.validate()` had exactly one
non-test call site, so its refusals stopped nothing, which is why
`create_app` calls `validate_production_gates()` directly at
[`backend/app/__init__.py:158`](../../backend/app/__init__.py). The refusals
below are produced by `_slo_and_cost_budget_errors` at
[`backend/app/config.py:477`](../../backend/app/config.py) and are appended by
both `validate_production_gates`
([`:628`](../../backend/app/config.py)) and `validate`
([`:706`](../../backend/app/config.py)), so the two cannot drift into
disagreeing about what is unsafe.

| Refusal | Condition | Why |
|---|---|---|
| `SLO_LATENCY_BUCKET_SECONDS` is not a bucket boundary | `SLO_ENABLED=true` | The histogram cannot answer it; the objective would be unmeasurable. |
| `SLO_LATENCY_TARGET_RATIO` outside `0 < x <= 1` | `SLO_ENABLED=true` | A ratio above 1 is met by any traffic at all. |
| `SLO_ERROR_RATE_MAX_RATIO` outside `0 <= x < 1` | `SLO_ENABLED=true` | A value of 1 permits every request to fail and still reports compliance. |
| `SLO_WINDOW_SECONDS` not positive | `SLO_ENABLED=true` | The evaluation period would be undefined. |
| `SLO_MIN_REQUESTS` below 1 | `SLO_ENABLED=true` | A window below one request is unreportable rather than strict. |
| A negative ceiling | `COST_BUDGET_ENABLED=true` | Almost certainly a sign error; `0.0` is how a scope is declared unbounded. |
| Both ceilings at `0.0` | `COST_BUDGET_ENABLED=true` | Declares a budget of nothing and enforces nothing. This is a false assurance. |
| `COST_BUDGET_BREACH_ACTION` outside the accepted set | `COST_BUDGET_ENABLED=true` | An unknown action names a behaviour that does not exist. |
| `COST_BUDGET_BREACH_ACTION=refuse` | `COST_BUDGET_ENABLED=true` | Selectable-looking but unkeepable: nothing measures a run's cost. |

Malformed input is refused earlier and harder. `SLO_*` and `COST_BUDGET_*`
numbers are read through `_strict_float` and `_strict_int` at
[`backend/app/config.py:62`](../../backend/app/config.py), which raise while the
`Config` class body is still executing rather than falling back to the default.
Falling back would substitute one number for another in the dangerous direction:
a ceiling of `12.50` misread as `0.0` turns "refuse this run" into "no ceiling at
all". `nan` and `inf` are rejected for the same reason — both survive `float()`
and both fail every comparison, so a `nan` ceiling would read as never breached
while looking configured.

`DEBUG` exempts all of this, matching the existing ingestion checks: a
production safety rule must not make local development impossible, and the
gateway is what stops a process from booting under an unsafe production
configuration.

## Remaining gaps

Recorded so the next change does not have to rediscover them. None of these is
addressable without a dependency decision or a data-model decision that belongs
to an owner.

1. **Distributed tracing.** Requires the OpenTelemetry SDK as a new dependency.
   `backend/requirements.txt` is a do-not-install pointer and CI plus both
   Docker builds resolve `uv.lock` through `uv sync --frozen`, which fails on a
   lock that does not match. Adding tracing therefore requires editing
   `backend/pyproject.toml` and relocking, not a hand-edit, and the lock is an
   owner decision because it touches every build.
2. **Alerting.** No alerting rule exists for either objective or for the cost
   ceiling. Until one does, an SLO is a declared threshold and a breach is
   silent. The formulas in this document are written to be transcribed into
   recording and alerting rules without modification.
3. **A cost meter.** Requires retaining provider `usage` per model call, a
   price table, and a per-run accumulation that survives the Celery worker
   boundary. That is a data-model change with a retention dimension, and
   [`architecture/data-model.md`](../architecture/data-model.md) is the
   authority for it.
4. **Enforcement wiring.** Once a meter exists, `run_preflight` is the seam, and
   `COST_BUDGET_BREACH_ACTION=refuse` becomes selectable in the same change that
   stops refusing it.
5. **Horizontal-scaling caveat.** The metrics registry is per process. Under
   more than one web worker, each instance reports its own counters and the
   objectives above must be evaluated on an aggregate, not per instance.

## Project-specific implementation status

**Owner:** `askthepeople-release-operator`

**Measured 2026-10-05 against commit `a410c9d`.**

- CURRENT: the settings and the refusals, in
  [`backend/app/config.py`](../../backend/app/config.py), with the operator
  contract in [`.env.example`](../../.env.example) and the tests in
  [`backend/tests/test_slo_and_cost_budget.py`](../../backend/tests/test_slo_and_cost_budget.py).
- CURRENT: the metrics the objectives are declared over, in
  [`backend/app/utils/metrics.py`](../../backend/app/utils/metrics.py).
- TARGET: alerting, the cost meter, enforcement wiring, distributed tracing, and
  multi-process aggregation, as listed in *Remaining gaps*.
- TRANSITION: the four Gate 4 items tracked in
  [`architecture/index.md` § *Status of record*](../architecture/index.md#status-of-record)
  that this document does not cover.

**Impact statement.** No runtime behaviour changes. Every setting defaults to
inert, and the two refusals only fire when an operator opts in with a value that
is wrong or names an unimplemented action. `Config` gains attributes that no
route, task, or service reads; the runtime settings route enumerates an explicit
allowlist rather than dumping the config, so nothing new is exposed. No stored
artifact, export, or disclosure changes, so there is no migration.

**Rollback.** Revert the config block and the `.env.example` block. There is no
schema, no persisted state, and no external contract to unwind.

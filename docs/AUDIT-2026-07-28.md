# ASKTHEPEOPLE Full Audit — 2026-07-28

## Executive decision

**Offline repository candidate:** **conditional GO** for continued private,
single-operator UI and test work. The complete frontend and backend suites pass.
A real container build/runtime smoke remains a CI-only gate on this workstation.

**Current public production:** **NO-GO**. Zep and Brave credentials exposed in
public Git history still matched current local and Railway configuration at
discovery time. Revoke and rotate them before any deployment work. The hardened
revision, required access key and origin policy, persistent volume, legacy
Vercel redirect, and deployed-revision verification also remain outstanding.

**Evidence claim:** **NO-GO** for describing any output as a poll, public
opinion, human validation, a forecast, a probability, a representative sample,
or a calibrated prediction. Every unaugmented run has zero human respondents.

The product now has a defensible purpose: widen a decision team's view of
possible paths, expose assumptions, and produce questions for separate
real-human research. It does not establish what people believe or what will
happen.

## Concept and purpose

### Baseline problem

The inherited experience blurred generated agents with people and treated
plausible model output as evidence about the future. That category error was
more serious than the old visual design: a polished interface would have made
an unsupported claim easier to trust.

Large actor counts are compute settings, not sample sizes. Generated follow-up
answers are additional model outputs, not interviews or testimony. Network modularity is not, by
itself, ideological polarization. Post-hoc keyword-related trace examples can
help inspect a run, but they are not citations, exact statement lineage, or
independent corroboration of the real world.

### Corrected product contract

The supported question is:

> Given these sources, explicit assumptions, generated profiles, platform
> rules, models, and prompts, what internally coherent scenario paths might this
> configured synthetic system produce?

The unsupported question is:

> What do people think, what will they do, or which outcome is most likely?

The application and documentation now require the wording “synthetic scenario,”
“possible path,” “generated profile,” “0 human respondents,” and “not a
forecast.” See [Methodology](METHODOLOGY.md), [Appropriate Use](APPROPRIATE_USE.md),
and [Validate With People](VALIDATE_WITH_PEOPLE.md).

### Residual concept risk

The name ASKTHEPEOPLE can still imply that people were consulted. The interface
must keep the disclosure visible, and any external marketing must explain that
“with people” is a handoff to separate research. A future rename remains a valid
product decision if that disclosure proves insufficient in user testing.

## Product and design

### Direction

The selected visual reference is Direction C: civic wayfinding rather than a
soft generic dashboard or a technical console. Its system uses warm paper,
charcoal, safety yellow, compressed display type, sharp geometry, strong
hierarchy, and route-like scenario paths.

The implemented redesign preserves:

- A plain-language decision-first entry point
- Visible “0 human respondents · not a forecast” disclosure
- Separate source, assumption, synthetic-path, and human-validation concepts
- PDF, Markdown, and TXT as the only advertised source formats
- A mobile single-column path, keyboard-visible focus, reduced-motion support,
  and explicit empty/loading/error/unauthorized states
- No fabricated metrics, sampled-human language, terminal decoration, emoji
  iconography, or generic floating-card composition

### Validation semantics

“Ask generated profiles” is an internal synthetic diagnostic. “Validate with
people” is an external research handoff. Clicking inside the application does
not recruit participants, obtain consent, or run a representative study.

## Product-truth remediation

Implemented in the worktree:

- Reframed README and report language as scenario exploration
- Added methodology, appropriate-use, validation, provenance, and deployment
  records
- Added visible synthetic disclosures to PDF, HTML, graph CSV, and generated
  response CSV exports
- Removed hardcoded numeric evidence-confidence claims
- Replaced political persuasion, market panic, regulation, and crisis-response
  templates with safer exploratory templates
- Replaced “future predictions” and “public opinion expert” instructions in
  reachable model prompts
- Relabeled generated-response exports and retained the old `/export/survey`
  path only as a compatibility alias
- Clarified that the legacy `polarization_index` field is network modularity Q
- Added a per-run manifest with revision, model resolution, limitations, and
  artifact hashes

Residual:

- The manifest is not append-only, independently signed, or durable without a
  volume
- No human-study record or external validation dataset is implemented
- No repeated-run calibration, held-out outcome evaluation, or guaranteed seed
  exists
- Models and external providers can still introduce unsupported details

## Runtime and architecture

### Correctness repairs

The worktree restores missing simulation-configuration methods, fixes undefined
runtime values, makes inter-process state files atomic, repairs task
serialization and dependency-injection mismatches, bounds paging and resource
inputs, validates paths, and makes report timeout responses return promptly.

### Current architecture limit

One Gunicorn worker is intentional because task and simulation state are
process-local. This is a deep operational limit, not a scaling preference.
Running multiple workers would fragment state.

The largest remaining seams are:

1. Task lifecycle and durable state
2. Provider runtime configuration
3. Evidence classification and provenance
4. Frontend workflow state

A future deep implementation should move task state to durable storage before
horizontal scaling. Provider secrets should remain an operator control plane,
not a general end-user feature.

## Security

### Critical open incident

Public commit `65403183ba37cefbcc73d23d9fdf666750db3ddc`
contained non-placeholder provider credentials in `.env.example`. Redacted
exact-value comparison confirmed that the historical Zep and Brave values still
matched current local and Railway production configuration at discovery time.
The repository is public and the commit is an ancestor of `origin/main`.

Provider-connected local work, staging, and production are **NO-GO** until
those credentials are revoked and replaced. Rotation must happen before an
operator-coordinated history rewrite. See
[Security Incident 2026-07-29](SECURITY-INCIDENT-2026-07-29.md).

### Fixed in the worktree

- Production fails closed without `SECRET_KEY`, explicit CORS origins, and an
  application access key
- HTTP API routes accept a bearer access key; browser WebSockets exchange it
  for a signed, resource-bound, single-use 60-second ticket
- Long-lived access keys are not placed in WebSocket query strings or Vite
  environment variables
- Runtime provider settings are disabled by default
- Provider URLs use an explicit allowlist and reject private endpoints by
  default
- Settings responses mask secrets
- HTTP request bodies, credentials, raw report-tool parameters, provider error
  details, and generated profile contents are excluded from production logs
- Production 5xx responses remove tracebacks and upstream exception text
- IDs and filesystem paths are constrained against traversal
- Upload bytes and extracted text, PDF pages, chunk overlap/count, graph paging,
  profile-generation concurrency, entity/profile counts, archetype expansion,
  follower controls, run rounds, generated follow-up questions, and related model-facing inputs
  have explicit ceilings
- Exported HTML escapes generated content and uses a restrictive CSP
- CSV cells that could execute spreadsheet formulas are neutralized
- The Docker runtime uses a non-root user
- CI includes tests, dependency audits, CodeQL, a checked-out-tree secret scan,
  an event-range scan, and an explicit all-ref history scan. Provider-specific
  rules cover the exposed credential formats. The history scan is expected to
  block until the known incident has been rotated and removed from every
  reachable public ref.

### Residual security limits

- The access model is one shared operator key: no accounts, roles, tenants,
  revocation list, audit identities, or per-project authorization
- Rate limiting is in-memory and therefore local to the single process
- Uploaded content remains an indirect prompt-injection and privacy risk
- The current `.env` is ignored, but matching Zep and Brave values were exposed
  in public Git history and require immediate provider-side revocation and
  replacement
- Existing uploaded artifacts may contain sensitive material and require an
  operator-owned retention/deletion review

## Deployment and operations

### Observed live topology

- The canonical working deployment is a unified Railway container serving the
  frontend, `/api`, `/ws`, and `/health` from one origin
- The legacy Vercel frontend is broken because it referenced a deleted backend
- Railway currently has no persistent volume, so uploads and generated
  artifacts are ephemeral
- Railway reports `source: null`; the live instance has no configured health
  path or drain window and therefore is not applying the repository's
  `railway.toml`
- The live runtime has no `APP_TOKEN`. The hardened revision will correctly
  fail closed until one is configured.
- A live read-only recheck at 2026-07-29 03:50 PDT confirmed that production
  still predates this hardening work: `/health` has no revision,
  unauthenticated `/api/settings` returns `200`, and `OPTIONS` advertises
  unauthenticated `POST`. The legacy Vercel URL still serves its old frontend
  instead of the repository redirect.

### Repository changes

- Railway now uses the repository Dockerfile and `/health`
- `/health` reports a build/platform revision
- Deployment starts only after successful main-branch CI and refuses an
  ambiguous main head
- The health gate requires the deployed revision to equal the tested revision
- GHCR release images are separated from the Railway source-build path
- Both Vercel configuration files temporarily redirect old traffic to the
  canonical Railway origin
- Render is documented as an alternative, not a second active frontend

### External release blockers

Before public production:

1. Preserve the current dirty worktree in a reviewed, secret-scanned patch or
   restricted backup. Review, commit, and merge its rewritten equivalent before
   treating any hardened workflow or configuration as active.
2. Revoke and rotate the historically exposed Zep and Brave credentials;
   confirm the historical LLM credential is revoked; review provider usage and
   billing.
3. Coordinate the public-history rewrite in a maintenance window: pause merges
   and deployments, use one named operator and a time-bounded force-push
   exception, rewrite all affected refs, immediately restore force-push
   restrictions, require re-clones, and verify a clean all-ref scan.
4. Connect the Railway service to this repository and `main`; the live service
   currently reports no connected source.
5. Protect `main` with reviewed pull requests, required CI/CodeQL/container
   checks, and
   force-push/deletion restrictions.
6. Create reviewer-protected, self-review-blocked, main-only
   `railway-production` and `ghcr-production` GitHub environments with
   administrator bypass disabled.
7. Put fresh environment-scoped `RAILWAY_PRODUCTION_TOKEN` and
   `PRODUCTION_APP_TOKEN` secrets in `railway-production`; remove and rotate the
   broad repository-level Railway token.
8. Disable direct Railway GitHub autodeploy.
9. Configure `SECRET_KEY`, `APP_TOKEN`, exact `CORS_ORIGINS`, provider
   credentials, provider URL allowlists, and the safe runtime flags in
   [Deployment](DEPLOYMENT.md).
10. Attach a Railway volume at `/app/backend/uploads`.
11. Deploy the Vercel redirect once and remove the stale Vercel API-base
   variable.
12. Deploy the hardened revision and confirm `/health.revision` matches it.
13. Exercise an authenticated upload → graph → simulation → report → export
   smoke test against production.

The repository cannot create the paid volume, environment protections, or
external secrets without an explicit operator decision.

## Lineage and license

ASKTHEPEOPLE descends from MiroFish and shares its initial Git history. It is not
an independently created system merely because GitHub does not display it as a
fork. The repository keeps AGPL-3.0 and now records the lineage and OASIS
dependency in [Provenance](PROVENANCE.md).

A public release still needs an asset and dependency-license inventory,
including legacy images, sample material, bundled fonts, and generated artwork.

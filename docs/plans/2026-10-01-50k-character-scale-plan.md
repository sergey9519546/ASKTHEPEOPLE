# 50,000-Character Population Scale Plan

> **Delivery state (2026-10-01).** Phases 1–4 are implemented and tested;
> Phase 5's documentation and eval wiring (this section, the env examples,
> the release verification) is in flight. Implemented surface:
>
> - **Phase 1** — `Config.POPULATION_TIER_4_ENABLED` (fail-closed),
>   `TIER4_ARCHETYPE_COUNT` / `TIER4_EXPANSION_FACTOR` /
>   `TIER4_PREPARED_PROFILE_MAX` / `TIER4_FOLLOWER_COUNT` /
>   `TIER4_FOLLOWER_COUNT_MAX`, the `api/routes` tier validation, and the
>   tier-4 preparation path in `simulation_manager._prepare_population_tier4`
>   (`backend/tests/test_population_tiers.py`).
> - **Phase 2** — `backend/app/services/persona_composition.py`: seeded,
>   deterministic variant composition over per-archetype shuffled axes
>   (posture, voice, disposition, topics) with an import-time axis-length
>   invariant; mandatory disclosure suffix on every generated profile
>   (`backend/tests/test_persona_composition.py`,
>   `backend/tests/test_follower_naming.py`, and the distinctness eval at
>   `backend/tests/evals/test_variant_persona_distinctness.py`).
> - **Phase 3** — per-round crowd action ceiling
>   (`TIER4_CROWD_ACTIONS_PER_ROUND_MAX`, deterministic down-sample) and
>   single-buffered `follower_actions.jsonl` writes; load test at
>   `backend/tests/test_follower_load.py` (45,000 followers, ~25 ms/round
>   against a 5 s budget).
> - **Phase 4** — preflight `population_tier_gate` +
>   `population_composition` checks with tier-resolved profile capacity,
>   `SimulationRunState` composition fields, and the declared-composition
>   display in `frontend/src/components/Step3RunWayfinder.vue`
>   (`backend/tests/test_preflight_tier4.py`,
>   `backend/tests/test_run_state_composition.py`,
>   `frontend/src/__tests__/step3-run-wayfinder.spec.js`).

A plan for scaling a single simulation run from the current hard cap of
1,000 characters to at least 50,000 **distinct** synthetic characters,
without violating the product truth contract, the OASIS runtime boundary,
or the resource-bounds policy.

Every character remains a scenario device. A population count is never a
sample size, and no character represents or predicts a real person.

## 1. Where the population comes from today (measured)

The current run composes characters from three engines. All three are live
code on the preparation or execution path:

| Engine | What it produces | Current cap | Where enforced |
|---|---|---|---|
| Entity-zip profiles | 1 LLM persona per graph entity | 500 entities / 500 profiles | `PREPARE_ENTITY_MAX`, `PREPARED_PROFILE_MAX` in `backend/app/utils/input_policy.py:24-28`; re-checked in `SimulationManager.prepare_simulation` and `backend/app/api/routes/prep_routes.py` |
| Archetype expansion | K centroids × M stochastic variants | K×M ≤ 500 | `ARCHETYPE_COUNT_MAX` (50), `ARCHETYPE_EXPANSION_MAX` (20), `PREPARED_PROFILE_MAX` in `backend/app/utils/input_policy.py:26-28`; archetype controls are **refused for new runs** under the v1 transition (`deprecated_control_not_supported` in `prep_routes.py` and `simulation_manager.py`) |
| Follower crowd | Rule-based lightweight agents | 500 | `FOLLOWER_COUNT_MAX` in `backend/app/utils/input_policy.py:30`, enforced in `backend/app/api/routes/execution_routes.py` start handler |

A fourth artifact exists but is **unreachable from production code**: the
`TIER_SPECS` population tiers in `backend/app/services/archetype_engine.py`
(largest: 300 LLM agents + 5,000 followers = 5,300). Only the module itself
and its own generator reference the tier table; no route or task resolves a
tier today. Phase 1 below wires a new tier rather than inventing a fifth
mechanism.

**Today's hard ceiling is 500 + 500 = 1,000 characters per run.** Raising it
to 50,000 is a bounded policy change plus three engineering workstreams —
not a rewrite.

## 2. What "50,000 different characters" must mean

A single run composes its population from three tiers of character, and the
split is load-bearing:

| Tier | Count | Generated by | Cost per character |
|---|---|---|---|
| Core LLM agents | ~200-500 | One LLM persona call per graph entity | One model call — expensive, bounded |
| Archetype variants | ~4,500 | Stochastic expansion of K centroids (no extra LLM calls) | Negligible compute, needs distinctness work |
| Follower crowd | ~45,000 | Rule-based `FollowerEngine` (`backend/app/services/follower_engine.py`) | Negligible compute, scales linearly |

The OASIS subprocess must **never** receive 50,000 LLM-driven agents: the
subprocess runs one model loop per agent, and a 50k-agent loop is neither
affordable nor observable. The crowd tiers are computed *around* the OASIS
core — variants as pre-expanded profiles in the platform config files, and
followers as post-hoc per-round reactions in the monitor thread
(`_follower_round_callback` in `backend/app/services/simulation_runner.py`),
which is exactly how the existing 500-follower path already works.

"Distinct" is the binding constraint. Today's archetype variants copy
`persona` and `bio` verbatim from the centroid and differ only in username,
age, platform counts, and jittered Big Five scores
(`ArchetypeEngine.expand_archetype` in `backend/app/services/archetype_engine.py`).
Fifty thousand clones of one persona paragraph is one character repeated,
not fifty thousand characters. Phase 2 closes this.

## 3. Design: the composition

A 50,000-character run composes as:

```text
K = 250 archetypes  (clustered from up to 500 source entities)
M = 18 variants per archetype  →  4,500 variant characters
    (each variant gets a compositional persona, not a verbatim copy)
F = 45,500 follower characters  (rule-based crowd, expanded behavior set)
    ─────────
    50,000 distinct characters
    OASIS core: the 4,500 variant profiles only — never the crowd
```

The follower crowd stays outside the OASIS subprocess entirely, exactly as
the existing path does. Variant profiles enter the OASIS config files
because they carry real personas; followers never do.

## 4. Phases

### Phase 1 — New population tier and raised bounds

Add `TIER_4` (`MASS_POPULATION`) to `TIER_SPECS` in
`backend/app/services/archetype_engine.py` with the composition above, and
raise the policy bounds in `backend/app/utils/input_policy.py`:

| Bound | Current | Proposed | Rationale |
|---|---|---|---|
| `ARCHETYPE_COUNT_MAX` | 50 | 250 | 250 centroids from ≤500 entities keeps ≥2 entities per centroid |
| `ARCHETYPE_EXPANSION_MAX` | 20 | 18 per archetype at tier 4 (bound to 50 for headroom) | 250 × 18 = 4,500 variants |
| `PREPARED_PROFILE_MAX` | 500 | 5,000 | Covers 250 centroids + 4,500 variants |
| `FOLLOWER_COUNT_MAX` | 500 | 50,000 | The crowd tier |

Constraints:

- **Env-gated, fail-closed.** The new tier activates only when
  `POPULATION_TIER_4_ENABLED=true` at runtime. The default run stays at the
  current 1,000-character ceiling; the bounds are read through
  `Config` so a deployment must opt in.
- **Re-enable the archetype path for tier-4 runs only.** Archetype controls
  are currently refused for new runs under the v1 transition
  (`deprecated_control_not_supported`). Tier-4 preparation re-allows exactly
  the archetype path with the new bounds, and only behind the same gate.
  The refusal stays for default runs.
- **A test per bound.** Every raised bound gets a test that fails when a
  request exceeds it, extending `backend/tests/test_resource_bounds.py`.
- **Acceptance:** tier resolves via `get_tier_spec`; a tier-4 prepare request
  passes validation behind the flag and returns 422 without it; default-run
  behavior is byte-identical to today.
- **Effort:** 1-2 days.

### Phase 2 — The distinctness engine (the real work)

Replace verbatim persona copying with **compositional persona variation**:
a deterministic, seeded generator that assembles each variant's persona from
a matrix rather than copying the centroid's paragraph.

```text
variant persona =
    role framing        (from the expanded role roster, 47 roles)
  + concern axis        (2-3 topics drawn from the centroid's interests,
                         rotated deterministically per variant)
  + disposition axis    (Big Five jitter already produces this — keep it)
  + constraint framing  (constraint_framing_text from the role contract)
  + disclosure suffix   (the mandatory fictional-scenario sentence)
```

Rules the implementation must hold:

- **No LLM call per variant.** The matrix is deterministic and seeded by
  `(archetype_id, variant_index)`, so a rerun reproduces the same population
  (the archetype engine's existing `random.seed` contract).
- **No two variants in an archetype share a persona string.** Enforced by a
  test that fails on collision.
- **Every persona keeps the fictional-scenario disclosure.** The compositional
  assembler appends the same disclosure sentence the verbatim copy carries
  today; the backend truth-term tests keep gating it.
- **Distinctness is measured, not asserted.** Add a distinctness eval to
  `backend/tests/evals/` (the existing `test_path_distinctness.py` is the
  model) that fails when the shingle Jaccard similarity between any two
  variant personas in an archetype exceeds a threshold.
- **Follower names follow suit.** `FollowerEngine.generate_followers` names
  every agent `follower_<behavior>_<index>` — fine for 500, but 45,500
  followers named `follower_amplifier_0042` need role- and topic-varied
  display names drawn from the same matrix so the crowd reads as characters
  rather than a counter.
- **Acceptance:** 50,000 generated characters contain zero duplicate persona
  strings, ≥45,000 distinct usernames, and pass the distinctness eval;
  rerunning generation for the same seed reproduces the same population.
- **Effort:** 2-3 days.

### Phase 3 — Throughput and memory

The follower round callback is the hot path. Today it runs O(N) per round
with per-agent `random` draws and appends line-by-line to
`follower_actions.jsonl` (`_follower_round_callback` in
`backend/app/services/simulation_runner.py`). At 45,500 followers:

| Concern | Today | Required change |
|---|---|---|
| Per-round cost | O(N) with N=500 | Same O(N) at N=45,500 is ~90× the work per round; batch the draws vectorized or chunked, and keep the per-round deadline bounded |
| Write throughput | Line-by-line append | Buffered batched writes (flush once per round, not once per action) |
| Action volume | ≤500 agents × 200 rounds | Cap crowd participation: the existing `activity_probability` distribution already throttles per-agent action rates; keep crowd-wide expected actions per round bounded (target ≤2,000/round) and make the cap a config value with a test |
| Memory | Agent lists in `cls._follower_agents` (process-local) | 45,500 dataclass instances is fine (~50 MB); the round-callback must not materialize per-action dicts for non-participants (it already skips them) |
| Ingest | `sync_observation_store` per round | Batch the crowd ingest; do not insert 45,500 rows one at a time |

Constraints:

- **The follower contract does not change.** Followers still never run inside
  the OASIS subprocess, still write to `follower_actions.jsonl`, still carry
  the same action schema. This is a throughput pass, not a redesign.
- **A load test at tier 4.** A test that generates 45,500 followers, computes
  10 rounds of actions against a fixture leader log, and asserts the round
  completes inside a deadline and the output line count matches the expected
  participation cap.
- **Acceptance:** 10 rounds at 45,500 followers complete inside the monitor
  deadline on a developer workstation; the OASIS round loop is never blocked
  by crowd work.
- **Effort:** 2-3 days.

### Phase 4 — Runtime gating and observability

- **Preflight extension.** `run_preflight` in
  `backend/app/services/simulation_preflight.py` gains tier-4 checks: the
  flag is on, the composition parameters multiply to the declared total, and
  the profile cap is not exceeded. A tier-4 run cannot start without passing.
- **Run-state visibility.** `SimulationRunState` already tracks
  `follower_twitter_count` / `follower_reddit_count`; add the declared
  population total and the per-round crowd action count so an operator can
  see the crowd behaving without opening the JSONL files.
- **Status presentation guard.** The run-status surface must present the
  population total as a *declared composition*, never as a sample size, and
  the frontend truth rail stays the enforcement point
  (`frontend/src/components/TruthRail.vue`). Add a test asserting the
  tier-4 status payload carries the composition fields but no
  sample-size-shaped field.
- **Acceptance:** a tier-4 run that fails a preflight check refuses to start
  with a named check; the status payload is guarded by test.
- **Effort:** 1-2 days.

### Phase 5 — Evals and the truth boundary

- **Distinctness eval** (from Phase 2) runs in the eval suite.
- **Comprehension guard:** the report layer must not describe the population
  in measurement language. The existing truth-term policing covers this;
  extend it to the new composition strings.
- **Documented limitation:** the plan document and the run-status payload
  both state that the crowd tiers are rule-based scenario devices, not
  simulated individuals, and that a 50,000-character population is a
  composition, not a sample.
- **Acceptance:** the eval suite passes with the new distinctness eval; no
  report or status surface presents the population as a measurement.
- **Effort:** 1 day.

## 5. Dependency order

```text
Phase 1 (tier + bounds, flag-gated)
   └─► Phase 2 (distinctness engine)   ── the long pole
          └─► Phase 3 (throughput)     ── independent of 2, can parallel
                 └─► Phase 4 (gating + observability)
                        └─► Phase 5 (evals + truth guard)
```

Phases 2 and 3 are independent and can proceed in parallel after Phase 1.
Phase 4 depends on both. Phase 5 lands last with the eval evidence.

## 6. Risks

| Risk | Mitigation |
|---|---|
| 50,000 profiles presented as a sample size | Composition fields, not sample-shaped fields, in the status payload; frontend truth rail unchanged; test-guarded |
| Distinctness work silently degrades into verbatim copies again | The Phase 2 collision test and the Jaccard eval both fail on copies; both run in CI |
| Crowd work blocks the OASIS round loop | The monitor-thread deadline and the Phase 3 load test both bound it; followers stay out of the subprocess |
| The archetype path re-enablement regresses the v1 boundary | The refusal stays for default runs; tier-4 re-allowance is flag-gated and tested both ways |
| Raising bounds invites unbounded requests | Every raised bound keeps a rejection test in `test_resource_bounds.py`; the flag is fail-closed |
| A rerun produces a different population | Seeded determinism is asserted by test; same seed → same 50,000 characters |
| Cost: 250 centroid LLM calls per tier-4 run | Bounded and declared in preflight; ~250 calls is within the existing per-run budget controls |

## 7. What this plan deliberately does not do

- **No 50,000 LLM agents.** The OASIS subprocess core stays bounded; the
  crowd is computed, not simulated.
- **No change to the follower action schema** or to where followers run.
- **No new fifth population mechanism.** The tier table already exists;
  this plan adds a tier to it.
- **No presentation of the population as a sample, panel, or representative
  group.** Every character is a scenario device; the truth contract is
  unchanged.
